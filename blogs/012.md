### Purpose
This volume defines the canonical data structures, schemas, and wire formats that act as the technical contracts for the DMWE platform. It translates the abstract concepts from earlier volumes into strict, typed representations. 

These schemas are presented in **TypeScript Interfaces** (for Volume IX Application SDK usage) and **Protocol Buffers (Protobuf v3)** (for Volume VIII low-power, binary wire transmission).

# Chapter 1: Core Messaging Envelopes (Volume VIII)

All communication across the mesh is encapsulated in a standard DMWE Envelope. This ensures the routing, QoS, and security managers can process packets without deserializing the semantic payload.

### 1.1 Protobuf Wire Format (`dmwe_core.proto`)
```protobuf
syntax = "proto3";
package dmwe.core;

enum QoSClass {
  QOS_BACKGROUND = 0;
  QOS_AI_INFERENCE = 1;
  QOS_VIDEO = 2;
  QOS_AUDIO = 3;
  QOS_REALTIME_INTERACTION = 4; // < 10ms latency requirement
}

enum PayloadType {
  TYPE_DESCRIPTOR = 0;
  TYPE_CAPABILITY_ADVERT = 1;
  TYPE_INTERACTION_OBJ = 2;
  TYPE_CONTEXT_FACT = 3;
  TYPE_RESOURCE_SYNC = 4;
}

message MeshEnvelope {
  string message_id = 1;         // UUID
  uint64 timestamp_ms = 2;       // Mesh-synchronized global time
  string sender_node_id = 3;
  string receiver_node_id = 4;   // Empty if broadcast
  string session_id = 5;
  QoSClass qos_class = 6;
  PayloadType payload_type = 7;
  bool is_encrypted = 8;
  
  // The opaque binary payload, decoded based on payload_type
  bytes payload = 9;             
}
```

# Chapter 2: Hardware & Capability Schemas (Volumes III & V)

When a module physically connects to the mesh, it must broadcast its `ModuleDescriptor`. Once authenticated, it registers its `CapabilityAdvertisements`.

### 2.1 The Module Descriptor (TypeScript SDK View)
```typescript
/** Volume III, Chapter 4: Module Descriptor */
interface ModuleDescriptor {
  moduleId: string;              // e.g., "DMWE-RNG-9942"
  manufacturer: string;
  productFamily: string;
  hardwareRevision: string;
  firmwareVersion: string;
  
  classes: ModuleClass[];        // SENSOR, COMPUTE, OUTPUT, POWER, etc.
  roles: DigitalRole[];          // VISION_NODE, AUTH_NODE, etc.
  
  resources: {
    battery: BatteryState;       // { level: 0.95, capacityMAh: 120 }
    compute: ComputeCapacity;    // { mips: 150, hasNpu: false }
  };
  
  security: SecurityProfile;     // { hasSecureElement: true, trustLevel: "PERSONAL" }
  spatialIdentity: SpatialPose;  // { defaultPlacement: "LEFT_INDEX_FINGER" }
}
```

### 2.2 Capability Advertisement (TypeScript SDK View)
```typescript
/** Volume V, Chapter 4: Capability Metadata */
interface CapabilityAdvertisement {
  capabilityId: string;          // e.g., "interaction.pointer.precision"
  version: string;               // e.g., "2.1.0"
  providerNodeId: string;
  
  lifecycleState: CapabilityState; // AVAILABLE, RESERVED, SUSPENDED
  
  // Quality of Capability (QoC)
  qoc: {
    latencyMs: number;
    accuracyScore: number;       // 0.0 to 1.0
    energyCost: EnergyProfile;   // LOW, MEDIUM, HIGH
    privacyClass: PrivacyDomain; // PUBLIC, PERSONAL, PRIVATE
  };
  
  dependencies?: string[];       // IDs of required underlying capabilities
}
```

# Chapter 3: Semantic Interaction Schemas (Volume VI)

This is the manifestation of the **Human Interaction Language (HIL)**. Applications never see raw gyroscope data; they subscribe to `InteractionObject` streams.

### 3.1 Interaction Grammar Enums (Protobuf)
```protobuf
package dmwe.interaction;

enum Verb {
  VERB_UNKNOWN = 0;
  VERB_SELECT = 1;
  VERB_MOVE = 2;
  VERB_ROTATE = 3;
  VERB_SCROLL = 4;
  VERB_PROJECT = 5;
  VERB_AUTHENTICATE = 6;
  VERB_UNDO = 7;
}

enum Modifier {
  MOD_NONE = 0;
  MOD_PRECISE = 1;
  MOD_CONTINUOUS = 2;
  MOD_SILENT = 3;
  MOD_SHARED = 4;
}

enum Target {
  TARGET_CURRENT_OBJECT = 0;
  TARGET_WORKSPACE = 1;
  TARGET_ROOM = 2;
  TARGET_IOT_DEVICE = 3;
}
```

### 3.2 Interaction Object (TypeScript SDK View)
```typescript
/** Volume VI, Chapter 4: Interaction Object */
interface InteractionObject {
  interactionId: string;
  timestamp: number;
  
  intent: {
    verb: Verb;
    modifiers: Modifier[];
    target: Target;
    spatialVector?: Vector3D;    // [x, y, z] for directional intents (e.g. Move/Point)
    scalarDelta?: number;        // Value change for continuous intents (e.g. Scroll)
  };
  
  origin: {
    capabilityId: string;        // e.g., "interaction.pointer"
    providerNodeId: string;      // The module that generated it
  };
  
  confidence: number;            // 0.0 to 1.0 (MeshOS uses this for conflict resolution)
  priority: PriorityClass;
  
  contextSnapshotId: string;     // Reference to the Context Graph state at this exact ms
  
  requiredFeedback: FeedbackLevel; // ACKNOWLEDGE, PROGRESS, CONFIRMATION
  completionState: Lifecycle;    // RECOGNIZED, EXECUTED, COMPLETED
}
```

# Chapter 4: Context & Cognitive Schemas (Volume VII)

The Context Engine continuously updates the **Human Digital Twin** and Context Graph. Facts are broadcasted as `ContextFact` payloads.

### 4.1 Context Fact (Protobuf)
```protobuf
package dmwe.context;

enum ContextLayer {
  LAYER_SENSOR = 0;
  LAYER_DEVICE = 1;
  LAYER_USER_ACTIVITY = 2;
  LAYER_ENVIRONMENT = 3;
  LAYER_APPLICATION = 4;
}

message ContextFact {
  string fact_id = 1;
  ContextLayer layer = 2;
  
  // Semantic key-value pair (e.g., key: "user.posture", string_value: "standing")
  string key = 3;
  oneof value {
    string string_value = 4;
    double numeric_value = 5;
    bool boolean_value = 6;
  }
  
  double confidence = 7;         // 0.0 to 1.0
  uint64 expires_at_ms = 8;      // Freshness boundary
  string provenance_node = 9;    // Which node derived this fact
}
```

# Chapter 5: Fast-Path Binding (Solving the Latency Edge-Case)

As identified in the architectural review, multi-hop semantic resolution is too slow for `<10ms` tasks like AR cursor tracking. Volume XI introduces the **DirectStream Binding**.

When an app successfully negotiates an `InteractionObject` subscription requiring ultra-low latency, the MeshOS grants a `DirectStreamToken`.

### 5.1 Direct Stream Packet (Optimized for Wire)
```protobuf
package dmwe.fastpath;

// Sent directly from Sensor Driver (Ring) to Application Render Loop (Glasses)
// Bypasses the Semantic Intent Engine entirely after initial handshake.
message FastPathStream {
  uint32 stream_token = 1;       // Short token negotiated via MeshOS
  uint64 timestamp_us = 2;       // Microsecond precision
  
  // Highly packed arrays for 1000Hz+ polling rates
  repeated float quaternion_wxyz = 3; 
  repeated float accel_xyz = 4;
}
```

### Implementation Note for Developers (Volume IX context)
By strictly defining these schemas, a developer building a Smart Home app in TypeScript never touches the `FastPathStream` or `MeshEnvelope`. They simply write:

```typescript
dmwe.subscribeToIntent({ verb: Verb.SELECT, target: Target.TARGET_IOT_DEVICE }, (interaction) => {
    if (interaction.confidence > 0.85) {
        smartLamp.toggle();
        dmwe.feedback.trigger(interaction.origin.providerNodeId, FeedbackLevel.ACKNOWLEDGE);
    }
});
```
The MeshOS uses the `InteractionObject` schema to automatically handle the translation, routing, and delivery from the Ring, through the protocol envelope, to this callback.
