## Part II: The Canonical Identifier System (DIDs)

### 2.1 The DMWE Identifier (DID) Architecture
In a unified graph model, string-based naming (e.g., `interaction.pointer.precision` or `sensor.imu`) introduces unacceptable overhead in memory, bandwidth, and parsing speed. To support real-time graph traversal across distributed low-power hardware, DMWE replaces strings with a rigid, structured, and globally unique naming convention.

Every Entity, Relationship, Event, and Schema in the ecosystem MUST possess an immutable **DMWE Identifier (DID)**.

#### 2.1.1 Anatomy of a DID String
The human-readable (and JSON-serializable) representation of a DID follows a strict URN-like structure:
`DID:<Domain>:<Authority>:<Type>:<ID>:<Version>`

*   **`DID`**: The fixed prefix identifying the URI scheme.
*   **`Domain`**: Usually `DMWE` (reserved for core standards) or a specific vendor/consortium domain.
*   **`Authority`**: The governing body that allocated the ID (e.g., `STD` for standard, `VENDOR` for third-party).
*   **`Type`**: A 3-character class indicator (e.g., `CAP` = Capability, `MOD` = Module, `EVT` = Event, `POL` = Policy).
*   **`ID`**: A 6-digit zero-padded unique identifier within that type.
*   **`Version`**: The semantic version (e.g., `v1`).

**Example (Standard DMWE Capability):**
`DID:DMWE:STD:CAP:000184:v1`
*Meaning: DMWE Standard Registry -> Capability -> ID 184 -> Version 1 (Precision Pointer).*

**Example (Third-Party Module):**
`DID:ACME:VENDOR:MOD:003217:v2`
*Meaning: ACME Vendor Registry -> Hardware Module -> ID 3217 -> Version 2.*

#### 2.1.2 Immutability Rules
*   Once an ID is assigned by an Authority, its core meaning **MUST NEVER change**.
*   A deprecated capability is NOT deleted from the registry, nor is its ID recycled. Its metadata is simply updated to `Status: Deprecated`.

### 2.2 The 80-Bit Binary Encoding (Machine Efficiency)
While the string representation is used for documentation, logging, and JSON tooling, the MeshOS runtime and network layer (Volume VIII) MUST use a fixed-width binary encoding. 

This guarantees $O(1)$ equality comparisons during graph traversal and minimizes radio payload size.

A Canonical DID is encoded as an **80-bit (10-byte)** binary structure:

| Field | Size (Bits) | Description |
| :--- | :--- | :--- |
| **Registry Type** | 8 bits | Maps to the `Type` string (e.g., `0x01` = CAP, `0x02` = MOD). |
| **Authority ID** | 16 bits | Maps to the `Authority` (e.g., `0x0000` = Standard, `0x1000` = Vendor A). |
| **Object ID** | 32 bits | Up to 4.29 billion unique objects per Type/Authority pair. |
| **Version** | 8 bits | Corresponds to the Major version (0-255). |
| **Reserved** | 16 bits | Reserved for future ecosystem expansion (set to `0x0000`). |

*(Note: 80 bits ensures extreme efficiency for 32-bit and 64-bit processors, requiring minimal masking or shifting to evaluate equality).*

### 2.3 The Dynamic Alias Table (Header Compression)
For `Critical Real-time` interaction classes (latency budget < 10ms, such as Fast-Path AR tracking), even a 10-byte ID represents unacceptable overhead if sent 1000 times per second.

DMWE employs a **Dynamic Alias Protocol**. 
1.  During the initial Session Handshake, the Primary Node and the secondary Module negotiate the required subgraph (e.g., establishing a Pointer stream).
2.  The Primary Node assigns a **1-byte or 2-byte volatile Alias** to the full 80-bit DID for the duration of that specific session.
    *   *Example:* `DID:DMWE:STD:CAP:000184:v1` is aliased to `0x0A`.
3.  All subsequent Fast-Path packets use only `0x0A` to identify the capability.
4.  If the session drops or the node migrates, the Alias Table is flushed, and aliases must be re-negotiated using the canonical 80-bit DIDs.

### 2.4 Registry Governance and Allocation
The standard requires a centralized (or federated but governed) authority to prevent collisions and maintain ecosystem integrity. This is the **DMWE Registry Authority (DRA)**.

#### 2.10.1 The 10 Canonical Registries
The DRA maintains version-controlled, machine-readable manifests (JSON/Protobuf) for the 10 canonical domains:
1.  **Organization Registry** (Vendor IDs)
2.  **Capability Registry** (CAP)
3.  **Module Registry** (MOD - Device classes)
4.  **Schema Registry** (SCH - Message formats)
5.  **Protocol Registry** (PRO - Communication standards)
6.  **Event Registry** (EVT - Standardized state changes)
7.  **Error Registry** (ERR - Standardized fault codes)
8.  **Workflow Registry** (WF - Reusable intent sequences)
9.  **Policy Registry** (POL - Privacy and security rules)
10. **Interaction Registry** (INT - Verbs, modifiers, targets)

#### 2.10.2 Allocation Block Ranges
The `Object ID` (32-bit) space within each registry is divided to allow decentralized innovation while protecting core standards:

| Range | Purpose |
| :--- | :--- |
| `0x00000000` – `0x0001869F` (0-99,999) | **Reserved Core** (DMWE Standard features only). |
| `0x000186A0` – `0x0007A11F` (100k-499k) | **Foundation Extended** (Approved standard extensions). |
| `0x0007A120` – `0x000C34FF` (500k-799k) | **Consortium** (Cross-vendor industry agreements). |
| `0x000C3500` – `0xFFFFFFFF` (800k+) | **Vendor-Specific** (Private innovation space). |

*(Vendors MUST use their assigned 16-bit Authority ID combined with the Vendor-Specific range to guarantee zero global collisions).*
