# DMWE Formal Foundations: The Unified Meta-Model and Graph Algebra
## Part I: The Unified Meta-Model (The Ontology)

### 1.1 The Shift to a Singular Truth
In distributed IoT and wearable systems, maintaining separate state architectures (e.g., a Device Graph, a Capability Registry, a Context Tree, and a Security Ledger) creates an **$O(N^2)$ synchronization problem**. As the system scales, the computational overhead required to keep these isolated models consistent exceeds the energy budget of wearable devices.

To solve this, DMWE introduces the **Unified Meta-Model (UMM)**. 

The UMM dictates that there is exactly **one canonical source of truth** in the DMWE ecosystem: a Universal Directed Property Graph. All runtime components, AI inferences, and state changes read from and write to this single semantic network. 

**Storage Agnosticism:** The UMM is a logical construct. The specification dictates the *mathematics and topology* of the graph, not its physical database implementation. A Primary Node (e.g., a Smartphone) MAY implement the UMM using an embedded Graph Database (like Neo4j or SQLite), while a low-power module (e.g., a Smart Ring) MAY implement its portion of the UMM as a flat, in-memory C-struct array.

### 1.2 The Five Primitives (Normative Definitions)
Every concept in the DMWE ecosystem MUST be represented as one of five mathematical primitives. No other foundational structures are permitted.

#### 1.2.1 Entities ($E$)
Entities are the nodes (vertices) of the graph. They represent anything that exists, whether physical or logical.
*   **Examples:** `Module`, `User`, `Intent`, `Task`, `Capability`, `AI Model`.
*   **Rule:** Every Entity MUST possess a Canonical Identifier (DID).

#### 1.2.2 Relationships ($R$)
Relationships are the directed edges connecting Entities. They provide the semantic link: `(Subject Entity) → [Relationship] → (Object Entity)`.
*   **Examples:** `provides`, `consumes`, `depends_on`, `authenticated_by`, `located_on`.
*   **Rule:** Relationships MUST be strictly directional but MAY be traversed bidirectionally by the MeshOS query engine.

#### 1.2.3 Properties ($P$)
Properties are key-value attributes mathematically bound to either an Entity or a Relationship. 
*   **Examples on an Entity (`Device`):** `battery = 92%`, `temperature = 33°C`.
*   **Examples on a Relationship (`provides`):** `latency = 5ms`, `reliability_score = 0.99`.
*   **Rule:** Properties represent scalar states, not other objects. If a property references another complex object, it MUST be refactored into an Entity and a Relationship.

#### 1.2.4 Events ($V$)
Events are immutable, time-stamped artifacts representing a state change in the graph. Instead of overwriting historical data, critical state changes append Event nodes to the graph, forming a temporal chain.
*   **Examples:** `PointerMoved`, `NodeDropped`, `AuthenticationSucceeded`.
*   **Rule:** Events MUST be immutable. They act as the distributed ledger for the interaction history and audit trails.

#### 1.2.5 Constraints ($C$)
Constraints are executable rules (Boolean predicates) bound to the graph. They dictate the legal boundaries of graph transformations.
*   **Examples:** `Latency < 10ms`, `PrivacyLevel == Local`, `Battery > 15%`.
*   **Rule:** The MeshOS Scheduler MUST evaluate Constraints before applying any Transformation Algebra to the graph. If a Constraint evaluates to `False`, the execution path is invalid.

### 1.3 Distributed Graph Architecture
The physical reality of DMWE is highly heterogeneous. A Smart Ring with 64KB of RAM cannot store the unified state of a 15-node mesh. 

#### 1.3.1 The Global View vs. The Local Bounded Context
*   **Global Materialized View:** The Primary Node (e.g., the user's phone or hub) maintains the fully materialized UMM. 
*   **Local Bounded Context (Sub-graph):** Secondary, low-power nodes maintain only a sub-graph containing the Entities and Relationships strictly necessary for their immediate capabilities.

#### 1.3.2 Graph-Diff Protocol
Nodes MUST NOT replicate full graph state. When an Entity changes (e.g., Ring battery drops from 40% to 39%), the node generates a **Semantic Graph-Diff**.
Instead of sending a JSON object, the node transmits a localized Triple update:
`UPDATE: (Entity: DID_Ring_1) -> [Property: Battery] -> (Value: 39%)`
The Primary Node applies this Diff mathematically, triggering sub-graph projections to dependent nodes in $O(1)$ time.

### 1.4 System Projections (Views)
The legacy silos (Capability Graph, Context Graph, Resource Graph) still exist logically, but they are no longer separately maintained databases. They are **Projections** (using the projection operator $\pi$, detailed in Part III).

When a subsystem requests data, the UMM dynamically generates a filtered view.

**Example 1: The Resource View**
The Scheduler requests a Resource View. The UMM applies a projection ($\pi_{Resource}$) that strips away Intents, Contexts, and Policies, returning only:
`(Device) → [Property: CPU]`, `(Device) → [Property: Battery]`.

**Example 2: The Security View**
The Security Manager requests an authentication check. The UMM applies a projection ($\pi_{Security}$) returning only:
`(User) → [authenticated_by] → (Certificate) → [grants] → (Permission)`.

Because all views are derived from the exact same meta-model, **it is mathematically impossible for the Security View to disagree with the Resource View regarding which devices are currently active in the mesh.**
